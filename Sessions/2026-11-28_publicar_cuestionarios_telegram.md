# 2026-11-28 — publicar_cuestionarios_telegram

## Tema
Publicación de los cuestionarios SEMANA_02 de Ciberseguridad ordenada desde la cuenta Telegram del usuario, mediante `agente_electronica_bot`.

## Contexto
- El sitio `cero97-ctrl/cuestionarios-ciberseguridad-s02` quedó **oculto** al cierre de la sesión anterior (repo `private`, Pages `false`, HTTP 404).
- El usuario pidió publicar desde su Telegram. El gateway `flujo_telegram.py` ya estaba activo (`/ping` → «Pong! El Gateway está activo y escuchando») y sólo reconocía `/start`, `/help`, `/ping`, `/diagnostico` y `/latex`.
- Se aplicó el guardrail determinista: NO meter la decisión en el chat. Se alertó al usuario y éste eligió **comando fijo** y **doble confirmación**.

## Decisiones (usuario)
1. La instrucción llega como **`/publicar`** (comando fijo), no como lenguaje natural interpretado por el asistente.
2. La publicación exige **dos pasos**: `/publicar s02` prepara y muestra el dry-run; `/confirmar s02 <token>` ejecuta el push y el cambio de visibilidad. Un `/confirmar` aislado no publica.
3. Alcance: los cuatro roles de SEMANA_02; se reutiliza el repo y el publicador existentes, sin duplicar la barrera anti-fuga.
4. Se mantiene el sitio oculto hasta que el usuario envíe personalmente los comandos desde su Telegram.
5. **Aclaración posterior del usuario**: no quería que el bot publicara por su cuenta, sino **darle la instrucción al orquestador (esta sesión) desde Telegram**. Confirmó «comando fijo». Por tanto los comandos `/publicar` y `/confirmar` pasan a ser un **puente** hacia la sesión de OpenCode; el bot ya no ejecuta el publicador.

- **Capa 2** `flujo_telegram.py`: nuevos comandos `/publicar` y `/confirmar` que solo analizan y delegan; `/help` actualizado. Los comandos existentes quedan intactos.
- **Capa 1** `directives/telegram_publicar_cuestionario.yaml` (SOP nuevo) y extensión de `directives/telegram_gateway.yaml` con `confirm_window_seconds: 900` y el mapeo de los comandos.
- **Barrera de reinicio**: el offset de Telegram se guardaba sólo en memoria, así que reiniciar el servicio podía reprocesar un `/confirmar` antiguo. Añadidas `leer_offset()`/`guardar_offset()` en `execution/telegram_api.py` (escritura atómica en `.tmp/telegram_offset.txt`) y persistencia antes de procesar cada update. Los updates pendientes se drenaron (0) antes de reiniciar; systemd relanzó el servicio con `Restart=always` (sin sudo interactivo) y quedó `active`.
- **Verificación**: `execution/test_telegram_publicar.py` 11/11 sin red (chat, texto libre, ruta inyectada, token caducado, token de otro chat, argv sin shell, resumen sin clave ni rutas, persistencia del offset); YAML y gateway importan bien; dry-run real devolvió los 4 `*_alumno.html` con los SHAs ya conocidos (`fe6d8c8…`, `323ee39…`, `3b91f6b…`, `d35cb16…`) y `publicado: false`; `/confirmar s02 tokenmalo123456` se rechazó con código 2 y sin efectos.
- El bot ya corre con el código nuevo; falta que el usuario pruebe `/ping` y `/publicar s02` desde su Telegram.
- **Puente Telegram → sesión (v2 del SOP)**: `execution/telegram_publicar.py::reenviar_a_sesion()` deposita el comando fijo en `POST /api/session/{id}/prompt` vía `opencode api post`, con `delivery: queue` (no interrumpe la respuesta en curso) e `id: telegram-<update_id>` (idempotencia: un reintento no duplica la orden). Antes de enviar, valida con regex cerrada que el texto sea **exactamente** `/publicar s02` o `/confirmar s02 <16 hex>` y que el `session_id` tenga forma `ses_...`; el texto libre se rechaza con código 2 y nunca llega al prompt. `flujo_telegram.py` dejó de importar `ejecutar_orden`/`resumen_telegram`: ahora importa `reenviar_a_sesion`/`mensaje_puente` y pasa el `update_id` como idempotencia.
- `OPENCODE_SESSION_ID` y `OPENCODE_BIN` se añadieron a `.env` (no versionado); el gateway los lee vía `load_dotenv()` ya cargado por `execution/telegram_api.py`. `directives/telegram_publicar_cuestionario.yaml` subió a v2.0.0 con `session_execution`: el orquestador ejecuta literalmente `python3 execution/telegram_publicar.py --chat-id 8671067338 --texto "<comando recibido>"` sin reinterpretar nada.
- **Verificación del contrato HTTP**: `opencode api post /api/session/ses_000…/prompt` con `{id,text,delivery}` devolvió 404 de sesión inexistente (servidor alcanzable, payload aceptado); `delivery: queue` y el `id` de idempotencia están en el OpenAPI 3.1 de v2.4.2. Se rechazó la opción `opencode run --session` porque interrumpía la respuesta en curso.
- **Pruebas ampliadas a 16/16** sin red: añadidos `test_puente_reenvia_comando_fijo_con_idempotencia`, `test_puente_rechaza_texto_libre_y_sesion_invalida`, `test_puente_construye_argv_sin_shell_y_parses_respuesta` (binario falso captura argv: `api post /api/session/ses_ABC123/prompt --data {...}`), `test_mensaje_puente_entrega_token_sin_afirmar_publicacion` y `test_gateway_reenvia_y_no_llama_al_publicador` (el gateway no invoca `ejecutar_orden`). Dry-run real tras el cambio: 4 `*_alumno.html` con los mismos SHAs. Bot reiniciado (PID 18833, `active`) con el código puente; sitio sigue en HTTP 404.
- **Fallo real del puente (HTTP 400) y corrección**: el usuario envió `/publicar s02` desde Telegram y el bot respondió «No pude entregar la orden a mi sesión: HTTP 400 Bad Request». Causa: el OpenAPI v2.4.2 define `Session.Message.ID` con patrón `^msg_`, pero el payload usaba `id: telegram-<update_id>`. Diagnóstico con `opencode api post ... --data '{"id":"telegram-999999",...}'` → `InvalidRequestError: Expected a string starting with "msg_" at ["id"]`. Corregido a `msg_telegram_<update_id>`; verificado con un POST de prueba (`resume:false`) que devolvió el mensaje encolado con HTTP 200, y el item de prueba se canceló con `DELETE /api/session/{id}/inbox/{inboxID}` para no dejar órdenes fantasma. Pruebas 16/16. El update que falló ya estaba acknowledgeado (offset guardado antes de procesar), así que el usuario debe reenviar el comando para generar un update_id y un token nuevos.
- **Incidente de commit corregido**: `update_repo.sh` hace `git add -A` y metió en el primer commit (`ae6f3dc`) los archivos ajenos del usuario (`cursos/LABORATORIO_I_FISICA/practicas/web/` y `publicar_lab1_practicas_web.sh`), aunque no se tocaron en disco. Se corrigió con `git reset --soft HEAD~1` + `git restore --staged` de esas rutas + nuevo commit (`0170908`) + `git push --force-with-lease`. Aprendizaje: con trabajo ajeno untracked en el árbol, **no usar `update_repo.sh` sin revisar**: hacer `git add` explícito y `git commit` directo (la divergencia ya era `0 0`).
