\needspace{5\baselineskip}
\section{\iconotexto{user-shield}{Tu rol en la práctica}}

Parte de su propia captura cruda y aplica el control equivalente: configuración, parche o regla de red. Repite el ataque para demostrar que falla y documenta el antes y el después.

\begin{itemize}[leftmargin=1.4em,itemsep=2pt,topsep=3pt]
  \item Leer su propia evidencia cruda y elegir el control que corta el ataque en el punto más barato.
  \item Aplicar el control y repetir el ataque para demostrar que ya no funciona.
  \item Documentar el antes y el después con los mismos comandos y la diferencia medida.
\end{itemize}

\needspace{5\baselineskip}
\section{\iconotexto{flag}{Qué aporta este rol al entregable}}

La mitigación aplicada, el comando de verificación y la comparación de resultados.

\needspace{5\baselineskip}
\section{\iconotexto{list-ol}{Ejemplo paso a paso}}

El rol Azul parte de su propia captura cruda, elige el control más barato y repite la misma medición. El entregable es la comparación antes/después, no la captura suelta: un control sin verificación es una intención.

\subsection{Fijar la línea base}

Antes de tocar nada se mide lo que hay. Se repiten los mismos comandos que se usarán después, porque comparar mediciones distintas no demuestra nada.

\begin{lstlisting}[style=estiloCodigo]
docker compose up -d
docker compose ps
ss -tulpn | grep -E ':8081|:3000|:2222' | tee semana_01/evidencia/azul_antes_servicios.txt
curl -sI http://127.0.0.1:8081/ | grep -i '^server' | tee semana_01/evidencia/azul_antes_server.txt
\end{lstlisting}

\subsection{Elegir el control por coste}

Entre dos controles que cortan lo mismo, se aplica el que se verifica con un comando y no rompe el resto del laboratorio. Aquí: cerrar el acceso de root por SSH y dejar de anunciar la versión del servidor web.

\subsection{Aplicar el control}

Cada cambio se hace con un comando reproducible. Si el contenedor no tiene el archivo esperado, se documenta como control no aplicado en lugar de simularlo.

\begin{lstlisting}[style=estiloCodigo]
docker exec objetivo-linux sh -c "sed -i -E 's/^#?PermitRootLogin.*/PermitRootLogin no/' /etc/ssh/sshd_config && sshd -t && (kill -HUP 1 || true)"
docker exec objetivo-linux sshd -T | grep -E '^(permitrootlogin|maxauthtries)' | tee semana_01/evidencia/azul_control_ssh.txt
docker exec objetivo-web sh -c "printf '\nServerTokens Prod\nServerSignature Off\n' >> /etc/apache2/apache2.conf && apache2ctl -k graceful"
\end{lstlisting}

\subsection{Repetir la medición y diferenciar}

La misma orden del inicio, sobre el sistema ya cambiado, y un diff explícito. Si el resultado no cambia, el control no sirvió y eso también se reporta.

\begin{lstlisting}[style=estiloCodigo]
ss -tulpn | grep -E ':8081|:3000|:2222' > semana_01/evidencia/azul_despues_servicios.txt
curl -sI http://127.0.0.1:8081/ | grep -i '^server' > semana_01/evidencia/azul_despues_server.txt
diff semana_01/evidencia/azul_antes_server.txt semana_01/evidencia/azul_despues_server.txt | tee semana_01/evidencia/azul_diff.txt
\end{lstlisting}

\section{\iconotexto{box-open}{Qué guardar en el repositorio}}

El informe incluye la tabla de control y verificación, el diff antes/después y una conclusión con el coste de cada control: cuántos comandos, cuánto riesgo de romper el servicio y qué queda expuesto después.

\begin{lstlisting}[style=estiloCodigo]
semana_01/
|-- informe.md
|-- evidencia/
|   |-- azul_antes_servicios.txt
|   |-- azul_despues_servicios.txt
|   |-- azul_antes_server.txt
|   |-- azul_despues_server.txt
|   |-- azul_control_ssh.txt
|   `-- azul_diff.txt
`-- README.md
\end{lstlisting}

\begin{itemize}[leftmargin=1.4em,itemsep=2pt,topsep=3pt]
  \item La medición de antes y la de después usan exactamente el mismo comando.
  \item Cada control tiene su comando de verificación y su salida real pegada.
  \item Si un control no se pudo aplicar, está dicho con el motivo, no omitido.
  \item El diff está en evidencia/ y el informe lo cita línea por línea.
\end{itemize}
